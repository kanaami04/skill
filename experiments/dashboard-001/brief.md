# Part 1 画面要件

## 1. 画面の目的

小規模チームのリーダーが、朝や会議の合間などに短時間開いて、次の2点をすぐに把握できるようにする。

1. 今日、自分が対応すべきタスクは何か。
2. 複数のプロジェクトのうち、どれに注意が必要か。

詳しい分析や編集はこの画面の目的ではない。ここで状況を把握し、必要ならプロジェクトやタスクの詳細へ移動する。

この画面を開いて10秒以内に、次の質問に答えられることを目標にする。

- 今日対応すべきタスクは何件あり、最優先はどれか。
- 注意が必要なプロジェクトはどれで、その理由は何か。
- 前回見たとき(昨日)から何が変わったか。

## 2. 対象ユーザー

- **誰が使うか**: 5名程度のチームを率いるリーダー。自分もタスクを持つ、プレイングマネージャー。
- **利用頻度**: 毎日数回(朝の始業時、会議の前後、夕方)。1回あたり数十秒から数分。
- **利用環境**: 主にデスクトップ。移動中や会議室ではスマートフォンでも確認する。
- **知識**: プロジェクト管理ツールには慣れている。初めて見る画面でも、説明なしに読めることを求める。

## 3. ユーザーの主要タスク

重要な順。

1. 期限切れ・今日期限・ブロック中の自分のタスクを確認し、手を付ける順番を決める。
2. 遅延・要注意のプロジェクトを見つけ、理由と期限を確認する。
3. 全プロジェクトの進捗と状態をひととおり眺める。
4. 最近のアクティビティで、チームの動き(レビュー依頼、状態の変化、コメント)を把握する。
5. 終わったタスクを完了にする。

## 4. 情報の優先順位

| 優先度 | 情報 | 補足 |
|---|---|---|
| 1 | 今日対応すべきタスク(期限切れ・今日期限・ブロック中) | 共通データでは未完了が5件。最優先が一目で分かること |
| 2 | 注意が必要なプロジェクト(遅延・要注意) | 共通データでは2件。状態の理由と期限を併せて示す |
| 3 | 全プロジェクトの進捗と状態 | 6件。進捗率、状態、期限、担当 |
| 4 | 今後7日以内に期限が来るタスク | 共通データでは4件 |
| 5 | 最近のアクティビティ | 8件。新しい順 |
| 6 | ナビゲーション | 現在地(ダッシュボード)が分かること |

## 5. 必須コンテンツ

全案に以下を含める。名称や見せ方は自由。

- **サイドナビゲーション**: ダッシュボード(現在地)、プロジェクト、マイタスク、カレンダー、チーム、レポート、設定。ダッシュボード以外はリンク先なし(`href="#"`)でよい。
- **ヘッダー情報**: ワークスペース名、ログイン中のユーザー名、今日の日付。
- **自分のタスク**: 共通データのタスク10件。期限、優先度、状態、所属プロジェクトを表示する。期限切れ・今日期限・ブロック中は、それ以外と区別できるようにする。
- **プロジェクトの進捗と状態**: 共通データのプロジェクト6件。進捗率、状態、期限、担当。遅延・要注意には状態メモを添える。
- **プロジェクト一覧**: 上と兼ねてよい。
- **最近のアクティビティ**: 共通データの8件。
- **優先度・状態の視覚表現**: 優先度(高・中・低)と状態の違いが見分けられること。**色だけに頼らない**(文字・形・位置などを併用する)。

置いてはいけないもの:

- 共通データにない指標、グラフ、数値(例: 「生産性スコア」「先月比+12%」)。集計値を出す場合は、共通データから計算できるものだけにする。
- 共通データにない人物、プロジェクト、タスク。

必須以外の要素(検索欄、通知、新規作成ボタンなど)は置いてもよい。ただし、見た目だけでよく、評価の対象外とする。

## 6. 機能要件(全案共通)

Vanilla JavaScriptで以下を動かす。保存はしない(再読み込みで初期状態に戻ってよい)。

1. **タスクの完了切り替え**: タスクを完了にする/元に戻す。関連する件数表示があれば連動して変わる。
2. **空の状態**: 「今日対応すべきタスク」(期限切れ・今日期限・ブロック中)をすべて完了にすると、その領域に「今日の対応はすべて完了」に相当する表示を出す。
3. **プロジェクトの絞り込み**: プロジェクト一覧を状態で絞り込む。選択肢は「すべて」「要対応(遅延・要注意)」「順調」「保留」「完了」。
4. **モバイルのナビゲーション**: 狭い画面ではサイドナビゲーションを折りたたみ、ボタンで開閉できる。

読み込み中とエラーの状態は不要(データはHTMLに埋め込むため)。

## 8. レスポンシブ対応の条件

- 確認するビューポート: **1440×900**(デスクトップ)、**375×812**(モバイル)。
- どちらの幅でも、ページ全体に横スクロールを出さない。表は、要素の中でのスクロールか、構造を変えることで対応してよい。
- モバイルでは、優先度1(今日対応すべきタスク)が最初の画面内に見え始めること。
- モバイルではサイドナビゲーションを折りたたむ(機能要件4)。
- モバイルで省略してよいもの: 優先度4〜5の情報の一部(件数を絞って「すべて見る」に置き換えるなど)。優先度1〜3は省略しない。
- 文字のはみ出し、重なり、切れがないこと。

## 9. 技術制約

- 1案につき、**HTMLファイル1つ**。ブラウザでファイルを直接開いて表示できること(`file://`)。
- CSSはHTML内の `<style>` に書く。
- JavaScriptは必要な場合だけ、Vanilla JSでHTML内の `<script>` に書く。
- ビルドツール、フレームワーク、外部UIライブラリは使わない。
- 外部フォント、外部画像、CDNなどのネットワーク依存を避ける。フォントはシステムフォントを使う。アイコンが必要ならインラインSVGか文字で表す。
- 基本的なアクセシビリティを満たす: 文字と背景のコントラスト、キーボード操作、フォーカス表示、操作要素のラベル。

## 10. プロダクト固有の特徴

- **Northstar(北極星)** という名前のとおり、「今どこに向かうべきか」を示すツールとする。機能が多いことより、判断を助けることを優先する。
- 利用者は毎日何度も開く。見慣れたあとも邪魔にならない、落ち着いた画面にする。
- ブランドカラーやロゴは未定。案ごとに決めてよい。

## 11. 仮定

- 「今日対応すべきタスク」は、期限切れ・今日期限・ブロック中の未完了タスクとする。
- ダッシュボードに出すタスクはリーダー本人の担当分だけとする。チーム全体のタスクはプロジェクト単位の件数で表す。
- データの保存、ログイン、他画面への遷移は扱わない。

# Part 2 実験設計(評価者用。Baseline には渡さない)

## 12. 実験の目的

Claude Code の Skill `/ui-design-rules` を適用すると、普段どおりの画面生成と比べて、AIっぽさを抑えた質の高い画面案を、より少ない修正時間で作れるかを検証する。

## 13. 実験の構成

```
experiments/dashboard-001/
├── brief.md              # このファイル
├── experiment-log.md     # 計測と評価の記録
├── comparison.md         # Rules の3案の比較(Skill が作成)
├── baseline/
│   └── index.html        # Baseline: 普段どおりの生成
├── rules/
│   ├── variant-a.html    # A. Clarity First
│   ├── variant-b.html    # B. Editorial Character
│   └── variant-c.html    # C. Operational Density
└── screenshots/          # 1440×900 と 375×812 の画面キャプチャ
```

### Rules の3案の方向性

| 案 | 方向性 | このダッシュボードで期待すること |
|---|---|---|
| A. Clarity First | 情報階層と分かりやすさ | 優先度1〜2が迷わず目に入る。初見でも読み方が分かる |
| B. Editorial Character | タイポグラフィ、余白、構成で個性を出す | Northstar らしさが出ている。それでいて10秒で答えられる |
| C. Operational Density | 情報密度と実務上の効率 | 1画面で全体が見渡せる。毎日何度も開く人が速く処理できる |

3案は配色違いではなく、情報の配置、レイアウト、タイポグラフィ、情報密度に明確な違いを持たせる。

## 14. 評価基準

**生成を見る前に確定する。** 評価中に基準を変えない。

### a. 10秒テスト(Part 1 §1 の3つの質問)

画面を開いてから10秒以内に答えられたかを、質問ごとに ○ / △(答えられたが迷った) / × で記録する。可能なら、ブリーフを読んでいない人にも試してもらう。

### b. 品質チェックリスト

`.claude/skills/ui-design-rules/rules/04-quality-checklist.md` の各項目を ○ / △ / × で評価する。

### c. AIっぽさのチェック

`.claude/skills/ui-design-rules/rules/02-anti-patterns.md` に該当するものがあるか。該当があっても、目的が説明できるなら減点しない。特に次の点を見る。

- 意味の違う情報を、同じ形のカードに入れていないか。
- 均等幅の指標カードを、理由なく並べていないか。
- 理由のないグラデーション、影、グロー、大きな角丸がないか。
- 共通データにない指標・グラフ・説明文で見た目を埋めていないか。
- サービス名を入れ替えても成立する画面になっていないか。

### d. 機能要件とレスポンシブ

Part 1 §6 の機能要件1〜4と §8 の条件を満たすか。

### e. 総合品質(1〜5)

| 点 | 基準 |
|---|---|
| 5 | そのまま採用して、仕様化に進める |
| 4 | 軽微な修正(文言・余白・色の微調整)で採用できる |
| 3 | 構造は良いが、修正が多い |
| 2 | 構造から見直しが必要。作り直しに近い |
| 1 | 採用できない |

**「採用可能」の判定**: 総合品質が4以上で、機能要件1〜4がすべて動き、どちらのビューポートでも大きな崩れがないこと。

## 15. Baseline と Rules の比較方法

### 条件をそろえる

- 両方とも**新しいセッション**で、同じモデルで実行する。
- Baseline と Rules に渡す要件は、どちらも Part 1 だけとする。
- 評価は同じビューポート(1440×900、375×812)で、同じブラウザで行う。
- 修正指示は、両方とも「採用可能」の判定に届くまで、同じ基準で出す。修正の上限は**5回**とし、届かなければ「採用不可」として記録する。
- 修正指示1回 = 1回と数える。1回の指示に見た目と機能・レイアウトの両方を含む場合は、主な方の種別で数え、備考に残す。

### Baseline

新しいセッションで、次のように依頼する。ブリーフの Part 2 を読ませない。

> `experiments/dashboard-001/brief.md` の「Part 1 画面要件」だけを要件として、画面を1案、`experiments/dashboard-001/baseline/index.html` に作ってください。Part 2 は読まないでください。ui-design-rules のSkillは使わないでください。

注意: `frontend-design` プラグインは、Skill の有無だけを比べるため、両条件とも**無効にして**実行する(`~/.claude/settings.json` の `enabledPlugins` で `false`)。実験の前に、新しいセッションのスキル一覧に出ていないことを確認する。

### Rules

別の新しいセッションで、次のように依頼する。

> `/ui-design-rules experiments/dashboard-001/brief.md の Part 1 を要件として、Part 2 §13 の構成で3案を rules/variant-a.html〜variant-c.html に作り、comparison.md に比較をまとめてください。`

3案を見たうえで1案を選び、必要なら修正指示を出す。採用案が決まったら、デザイン仕様(`design-spec.md`)の作成までを依頼する。

### 比べるもの

1. **Baseline の1案 と Rules の採用案**: 評価基準 a〜e、初回生成時間、採用可能になるまでの時間、修正回数。
2. **Rules の3案どうし**: 配色以外(配置、レイアウト、タイポグラフィ、情報密度)に明確な違いがあったか。
3. **Rules の3案すべてと Baseline**: Rules のどの案も Baseline より劣るなら、そのこと自体を結果として記録する。

### 時間の測り方

- **初回生成時間**: プロンプトを送ってから、Claude が完了を報告するまで。許可の確認待ちも含む。
- **採用可能になるまでの時間**: 最初のプロンプトを送ってから、評価者が「採用可能」と判定するまで。評価や修正指示を書く時間、Rules で3案から選ぶ時間も含む。
- 時刻は `experiment-log.md` に記録し、分単位で計算する。

### 解釈の注意

- この1回だけで結論を出さない。別の画面でも同じ実験をして、再現性を見る。
- Rules は3案を作るため、初回生成時間は長くなりやすい。主に「採用可能になるまでの時間」と「修正回数」で比べる。
- 評価者がブリーフとルールを知っているため、Rules に有利な評価になりやすい。10秒テストには、できればブリーフを読んでいない人に協力してもらう。
