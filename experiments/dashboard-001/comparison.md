## 案ごとの評価

### A. Clarity First

- 方向性: 「今日対応するタスク」を最上段の主役にし、対応順の番号と「最優先」ラベルで着手順を示す。「注意が必要なプロジェクト」は枠なしの行(左の太い線+状態名+メモ+期限)にして、タスクの枠とは別の形にした。
- 長所:
  - 読む順番が明快で、初見でも説明なしに読める。
  - 件数の内訳(期限切れ 2 / ブロック中 1 / 今日期限 2)が見出しの横に出る。
  - タスク行は「優先度(棒+文字)」と「状態(形+文字)」で、色だけに頼らない。
  - 完了済みは別見出しにまとまり、戻しやすい。
  - 注意プロジェクトに「自分の未完了タスク」(T-101、T-104 など)を添えた。データから導いた関連で、「注意」と「今日のタスク」がつながる。
- 短所:
  - 無難で、サービス名を入れ替えても成立する。
  - タスク行にバッジが多い(最優先・期限切れ・ブロック中・今日期限・状態)。
  - モバイルは縦に長く(3,769px)、アクティビティ(優先度5)は最下部。
- 適した用途: 初めて使う人が多い、または説明なしで使わせたいチーム。仕様化・本実装への移植がもっとも素直。
- 情報の優先順位が伝わるか: 伝わる(作成者の見立て)。
  - 1番目の問い: 見出し横の「5件」と「最優先」ラベルで答えられる。
  - 2番目の問い: 最初の画面の下端で「遅延 ヘルプセンター移行」が見え始める。要注意の P1 はスクロールが必要。
  - 3番目の問い: 右カラムの「昨日から 3件」。
- プロダクト固有の特徴があるか: 弱い。星の印と紺色のみ。「判断を助ける」という方針は、最優先の明示や関連タスクの表示に出ている。
- 改善が必要な点:
  - 最優先の理由を文章で一言添えるか検討(今は期限チップが理由を兼ねる)。
  - バッジの整理(ブロック中と状態「ブロック」が重複しないようにする)。
  - モバイルでの長さの調整。
- スクリーンショット: `screenshots/variant-a-1440.png`、`variant-a-375.png`、`variant-a-1440-full.png`、`variant-a-375-full.png`、`variant-a-1440-empty.png`(空の状態)、`variant-a-375-nav.png`(ナビ展開)

### B. Editorial Character

- 方向性: 画面の頭に、データから組み立てた一文を置く。例: 「今日対応するのは5件。最優先は『ヘルプ記事の移行範囲を確定する』(期限切れ 2日)。」その下に件数・注意プロジェクト数・昨日からの動きを添える。以降は罫線で区切った本文。最優先タスクだけを大きなセリフ体の見出しにする。
- 長所:
  - 3つの問いのうち2つ(件数と最優先、注意の件数)は、見出しを読むだけで答えられる。
  - 「北極星」を、星の印・朱色・二重罫・大きな日付で出し、Northstar らしさがもっとも出ている。
  - 優先度は四角い印(高=塗り、中=枠、低=薄い)で、文字と形を併用している。
  - 角丸・影・グラデーション・カードがない。
  - 今後7日を「日割りの罫線」にして、日付ごとの偏りが見える。
- 短所:
  - 縦に長い(1440幅で2,338px、モバイルで4,778px)。
  - 最初の画面(900px)には今日の5件がぎりぎり入るだけで、プロジェクト一覧(1,154px〜)とアクティビティ(1,077px〜)は下にある。
  - 毎日何度も開くと、大きな見出しが冗長になる可能性がある。
  - セリフ体は OS 依存(Windows / Android の明朝系フォントが未確認)。
  - リードの文は生成した文章で、「説明文で埋める」アンチパターンと紙一重(下表)。
- 適した用途: 朝に腰を据えて状況をつかむ使い方、プロダクトの個性を強く出したい場合。
- 情報の優先順位が伝わるか: 伝わる(作成者の見立て)。
  - 1番目の問い: 見出しだけで答えられる。
  - 2番目の問い: 右上の「注意が必要なプロジェクト」。遅延と要注意のメモも並ぶ。
  - 3番目の問い: 見出し下の一文で件数(3件)は分かるが、中身(右カラムの「昨日から 3件の動き」)は最初の画面の下(1,077px〜)。内容まで答えるにはスクロールが必要。
  - 1440×900 の最初の画面で答えられるのは、1番目と2番目の問い。
- プロダクト固有の特徴があるか: ある。3案でもっとも強い。
- 改善が必要な点:
  - リードの長さと、モバイルの縦の長さの調整。
  - プロジェクト台帳を状態の深刻な順に並べ替える(今は ID 順で、注意は右カラムにある)。
  - セリフ体のフォールバック確認。
- スクリーンショット: `screenshots/variant-b-1440.png`、`variant-b-375.png`、`variant-b-1440-full.png`、`variant-b-375-full.png`、`variant-b-1440-empty.png`、`variant-b-375-nav.png`

### C. Operational Density

- 方向性: 先頭に「5件を今日対応 / 最優先 T-101 … 期限切れ 2日 / 期限切れ・ブロック中・今日期限・要対応プロジェクト・昨日から」の1本の帯。その下は、10件のタスクを1つの表(今日対応 / 今後7日以内の2グループ)にまとめた。プロジェクト表は、深刻な順(遅延 → 要注意 → 順調 → 保留 → 完了)に並べ、状態メモも同じ行に出す。
- 長所:
  - 1440×900 に**全領域が収まる**(ページ高 900px、スクロールなし)。
  - 毎日何度も開く使い方に合う。行は1〜2行で、列で見比べられる。
  - 帯の数字は、均等カードではなく1本の行。
  - 左端の色線(期限切れ・ブロック=赤、今日=琥珀)に、文字と形の状態表示を併用している。
  - 優先度は ▲高 / ■中 / ▽低(形+文字)。
- 短所:
  - 13px基準で、初見の読みやすさは3案で最低。文字の強弱の差も小さい。
  - Northstar らしさは薄く、一般的な業務ツールに見える。
  - モバイルは表が行カード状に組み替わり、1行に項目が詰まる(2,420px)。
- 適した用途: 毎日・1日数回開き、一覧から素早く処理するプレイングマネージャー。
- 情報の優先順位が伝わるか: 伝わる(作成者の見立て)。
  - 1番目の問い: 帯だけで答えられる。
  - 2番目の問い: プロジェクト表の最上段2行(遅延・要注意)が深刻な順で並び、メモが同じ行にある。
  - 3番目の問い: 帯の「昨日から 3件」と、右の「今日 10/15」の見出し。
  - 1画面にすべて収まる点は3案で最良。
- プロダクト固有の特徴があるか: 弱い。ダークのサイドバーと帯に特徴はあるが、サービス名を入れ替えても成立する。
- 改善が必要な点:
  - 本文の文字を13px→14px程度に上げる余地(1画面に収まる条件とのトレードオフ)。
  - 帯の最優先の表現と、表中の「最優先」の重複整理。
  - モバイルの行の見せ方。
- スクリーンショット: `screenshots/variant-c-1440.png`、`variant-c-375.png`、`variant-c-1440-full.png`、`variant-c-375-full.png`、`variant-c-1440-empty.png`、`variant-c-375-empty.png`、`variant-c-375-nav.png`

## 仮定(実装時に置いたもの。ブリーフに明記のないもの)

1. 「昨日から変わったこと」は、アクティビティのうち日付が今日(10/15)のもの3件とした。前回の閲覧時刻が不明のため。
2. T-110 を「未完了に戻す」ときの状態は「未着手」とした。データに元の状態がないため。
3. 「最優先」は、未完了の「今日対応」タスクのうち、期限が古い順 → 優先度が高い順 → ID 順で最初のもの(T-101)。対応順の番号も同じ並び。
4. 完了したタスクは所属するグループ(今日対応 / 今後7日)に残し、完了済みとして表示する。「今日対応」が0件になると「今日の対応はすべて完了」を出す。完了にしたタスクは数えない。
5. 「今日対応」の件数内訳は、重複しないよう「期限切れ > ブロック中 > 今日期限」の順で1つだけ数える(T-103 は「ブロック中」。ただし行には「今日期限」も表示)。
6. 「自分の未完了タスク」(注意プロジェクトの下)は、タスクの所属プロジェクトから導いたもので、共通データにない情報は足していない。
7. ブランドカラーとロゴは未定のため、星(北極星)の印と色は各案の仮置き。
8. 進捗率は完了数 ÷ 全タスク数から計算し、ブリーフの表の値と一致している。

## 推奨案(Claude)

- 推奨: **A. Clarity First**(ただし、下の条件で B または C が上回る)
- 理由:
  - 要件適合性: 3つの問いと、優先度1〜3の領域(§4)を過不足なく満たす。最優先の明示と注意プロジェクトの理由(メモ・期限・自分のタスク)が、最初の画面で完結する。
  - 分かりやすさ: 「説明なしに読める」(§2)を一番素直に満たす。読む順番が固定で、ブランド色の働きが単純。
  - 実装品質: 仕様化(`design-spec.md`)と本実装への移植が最も素直。装飾が少なく、既存の技術スタックに載せやすい。
  - 注意: A は Northstar らしさが最も弱い(§10 の「プロダクト固有の特徴」)。これは B の方向に寄せる余地がある。
- 他案から取り込むとよい点:
  - **C から**: プロジェクト一覧を状態の深刻な順に並べる。状態メモを一覧の行に出す(A は行の下に出している)。件数の内訳を1行にまとめる。
  - **B から**: 最優先を一文で示す短い見出し。今後7日を日割りで見せる表現。優先度を形で示す印。
- 選び方の目安(決めるのはユーザー):
  - **毎日何度も開き、処理を速くしたい** → C。1画面で全体が見える点が最大の強み。
  - **Northstar らしさを画面の個性にしたい**、朝にじっくり見る → B。ただし縦の長さとフォントの確認が必要。
  - **初見でも迷わず、仕様化を急ぎたい** → A。

## 決定(ユーザー)

| 活動を控えめにした | 本文を薄い色にし、名前と時刻だけを濃く残した。 |

### 2. 文字が多い → 要件で必須でない文字を削った

| 削ったもの | 理由 |
|---|---|
| タスクの ID 列(T-101 など)と、表の「最優先」バッジ | ID は必須要件になく、最優先は要約バーに出ているため(重複)。 |
| タスクの備考の2行目(「ベンダーの回答待ち」など) | 同じ内容が状態メモ・アクティビティに出ているため。1行1タスクになり、行の高さも減った。 |
| グループ見出しの説明(「期限切れ・今日期限・ブロック中」「10/16〜10/22」) | 見出しの件数だけで足りるため。 |
| プロジェクトの完了数/全数(9/24 など) | 進捗率が同じ情報を示すため。 |
| 絞り込みボタンの件数、「昨日から N件」バッジ(アクティビティ見出し) | 要約バーや見出しの件数と重複するため。「未完了 9 / 完了 1」は「未完了 9件」にした。 |

実測(1440幅の本文の文字数。空白を除く): **1,359 → 1,164 文字(約14%減)**。ブリーフの必須要素(タスク10件の期限・優先度・状態・プロジェクト、プロジェクト6件の進捗・状態・期限・担当・状態メモ、アクティビティ8件)は残している。

### 3. 左の線を外した

修正前は 8 か所(要約バーの左の太線、期限切れ・ブロック中・今日期限の各タスク行、遅延・要注意の各プロジェクト行、ナビの現在地、ヘッダーとバーの縦の区切り線)にあった。修正後は**すべて外した(0 か所)**。

- 状態は、すでに文字・形・色で示している(期限切れ=赤い「期限切れ 2日」、ブロック=赤い丸+「ブロック」、遅延=赤い菱形+「遅延」、要注意=琥珀の三角+「要注意」)。線は同じ情報の重複だったため、残す必要がないと判断した。
- ナビの現在地は、背景色の差と太字で示す。
- もし「期限切れ・ブロック中の行だけは線で目立たせたい」場合は、その行だけに戻せる。
