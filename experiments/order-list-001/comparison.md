## 共通の土台(`rules/03-design-protocol.md` Step 2)

- 画面の種類と守る慣習: 管理画面。左ナビ(狭い画面では折りたたみ)、ページ見出し「注文」、主要な領域は囲む、比較する情報は表またはリスト。依頼文の「テンプレートに安易に寄せず」は、構造を崩すのではなく、**情報の出し方(要対応を「理由と次の対応」で見せる)と色・文字で**応える。
- 焦点(最初に目に入れたい1か所): **要対応の7件と、その理由・次の対応。** 並びは「超過 → 決済エラー → 今日発送 → 入金確認 → 新規」の緊急順。
- 囲む単位: 注文一覧の領域と、詳細の領域だけ(C は「要対応」の領域も)。行・見出し・ナビは囲まない。入れ子にしない。
- 強調の段階: 焦点 = アクセント(A 橙赤の文字、B 緑青の文字、C 黄の面+黒の札)と大きさ / 注意 = 太字 / 通常 = 標準。アクセント色は案ごとに1色。
- 状態の見分け(色だけに頼らない): 注文状態は**進捗を表す円(○◔◑◕●、キャンセルは斜線)+文字**。支払い状態は文字と太さ(未入金は太字、決済エラーは「!」+強調)。
- 特に出さない AI典型: 左の色線、状態ごとの淡いバッジ、指標カードの列、動かない検索欄や通知、共通データにない数値。
- 置いた仮定: 下の「仮定」を参照。

## 案ごとの評価

### A. Practical

- 長所: 最初の画面で、7件・理由・次の対応・発送期限・金額が1画面に収まる。表のまま比較でき、毎日使う人の速さを優先できている。「要対応」の固定で、新しい順の並びを壊さずに焦点を作った。
- 短所: 一番「管理画面のテンプレート」に近い。依頼の「個性」は、橙赤の使い方と「対応」の列にとどまる。1行10項目で、初めて見る人には密度が高い。
- 適した用途: 毎日・1日に何度も開き、慣れた人が一括処理する運用。
- 改善が必要な点: 詳細ドロワーを開くと、商品・配送・支払いの列が自動で隠れる(幅が足りないため)。開いた行の枠線(2px)がやや強い。同じ情報の重複(決済エラー)。
- スクリーンショット: `screenshots/variant-a-1440.png`、`variant-a-375.png`、`variant-a-desktop-detail.png`、`variant-a-desktop-bulk-ng.png`

### B. Balanced

- 長所: 「今日やること(要対応 7 / 発送準備に進める 2)」と「注文状態」が左のレールに分かれ、10秒テストの3問すべてに、レールの数字と一覧の1行目で答えられる。詳細が常に右に出ていて、「一覧 → 詳細」の往復がない。デスクトップの最初の画面で、全体のバランスが最も良い。
- 短所: 1件が3〜4行で、一度に見える件数が少ない(約6件)。商品名は幅によって省略される。受信箱のような見た目なので、「注文を表で比べる」感覚は弱い。
- 適した用途: 初めて使う人にも、毎日使う人にも無理がない。「次の1件を片付ける」流れの運用。
- 改善が必要な点: 詳細ペインの「要対応」が、行の1行目と重複する。「すべて」に切り替えたとき、要対応がまとまらない(新しい順のため)。
- スクリーンショット: `screenshots/variant-b-1440.png`、`variant-b-375.png`、`variant-b-desktop-bulk-ok.png`、`variant-b-mobile-detail-mobile.png`

### C. Presentable

- 長所: 「今日中に発送する」「購入者に連絡する」と、**何をするかが見出しになる**ので、「それぞれ何をすればよいか」に最も直接に答える。焦点が最も強く、プロダクトの個性(要対応を取りこぼさない)が見た目に出ている。詳細(中央のダイアログ)は、明細・注意・注文情報が広く読める。
- 短所: 最初の画面の大半が要対応パネルで、**発送準備に進める注文と一覧は画面の外**(見出し横のボタンで一覧へ移動できる)。要対応が上と下の両方に出る。一覧が縦に長い(2784px)。
- 適した用途: 少人数のショップが、始業時に「まず今日の対応を確認する」使い方。
- 改善が必要な点: 一覧に出る要対応の理由が、上のパネルの繰り返し。モバイルでは、要対応パネルが長く、一覧の見出しは約1,190px 下(1.5画面分)にある。黄は焦点専用にしてあるが、他の画面と比べて「色が強い」と感じる人がいるかもしれない。
- スクリーンショット: `screenshots/variant-c-1440.png`、`variant-c-375.png`、`variant-c-desktop-detail.png`、`variant-c-1440-full.png`

### 機能要件の確認(実ブラウザ)

3案 × 2ビューポートで、同じ手順を実行した(デスクトップ 27項目、モバイル 30項目。全項目合格)。

- 絞り込み: 8つすべてで、件数の表示と一覧の件数・注文番号が期待どおり(要対応 7、新規 3、確認済み 5、発送準備中 3、発送済み 4、配達完了 2、キャンセル 1)。
- 検索: 注文番号(`#` 付きも)、購入者名、商品名の部分一致。絞り込みとの組み合わせ。0件のとき空の状態を出し、解除できる。
- まとめて発送準備へ: 実行できない選択(#10243 入金待ち、#10248 新規)では、ボタンが無効になり、理由と「進めない注文の選択を外す」を出す。#10245・#10244 を実行すると状態が「発送準備中」に変わり、確認済み 5→3、発送準備中 3→5、要対応は 7 のまま(この2件は要対応ではないため)、発送準備に進める注文は 0 件になる。
- 詳細: 明細(小計・送料・代引き手数料・合計。**18件すべてで、計算結果が共通データの合計と一致**)、配送先、支払方法、支払期限、発送期限、備考。一覧に戻れる。
- モバイル: ナビの開閉、要対応が最初の画面内に見え始める(A・B・C とも、最初の要対応の行の上端が 812px 以内)。

## 推奨案(Claude)

判断の順: 画面の種類に見えるか → 焦点 → 要件 → プロダクトらしさ。

- 推奨: **B(Balanced)**。ただし C と迷う。決めるのは人間の第一印象で、私の評価は高めに出ている。
- 理由:
  1. 3案とも管理画面に見え、焦点(要対応の7件)も一致した。
  2. 10秒テストの3問(7件と何をするか / 今日発送 / 発送準備に進める)に、**最初の画面の中で**答えられるのは B(レールの数と1行目)と A。C は3問目が画面の外。
  3. 要件の「情報の優先順位やレイアウトを工夫し、個性と実用性を両立」に対して、B は表の型から離れたうえで、毎日使う操作(選んで一括実行、詳細の確認)を崩していない。A は実用は最も高いが個性が弱い。C は個性が最も強いが、一覧と一括操作が下に回る。
- 他案から取り込むとよい点:
  - C の「次の対応を見出しにする」書き方(B の1行目の理由に取り込める)。
  - A の「要対応を先頭に固定した全件表」(B の「すべて」表示で、要対応が散らばる問題を解く)。
- 迷う点: 「テンプレートに安易に寄せず、個性を」を最優先するなら C。毎日使う処理の速さを最優先するなら A。

## 置いた仮定と、確認したい点

- 「発送準備中にする」を、複数選んだ中に1件でも進められない注文があれば**実行しない**(進められるものだけ実行、にはしない)。理由を見せて、「進めない注文の選択を外す」で解消する形にした。進められる分だけ実行する方が良ければ、変える。
- 「要対応」のタブ・レールの並びは緊急順(超過 → 決済エラー → 今日発送 → 入金確認 → 新規)。要件にない順序なので、確認したい。
- B は、開いたとき「要対応」を選び、一番上の注文の詳細を出す。デスクトップでは一覧と詳細が同時に見えるため、「一覧に戻る」ボタンはモバイルだけに出る。
- A・C には、補助の入口として「発送準備に進められる注文を選ぶ」ボタンを足した。B は、レールの「発送準備に進める」で絞り込む。必須の絞り込み8つとは別。
- 今日は 2026年10月16日(金)10:30 に固定(端末の日時は使わない)。画面上の日付はその文字列。
- 配送先は都道府県と市区町村まで。詳細の住所・電話番号は出していない。
- 共通データから計算できない指標・グラフは出していない。
