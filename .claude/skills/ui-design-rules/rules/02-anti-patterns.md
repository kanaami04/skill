# AIっぽいUIを避けるためのアンチパターン

以下を絶対禁止とはしない。**採用する場合は、目的と必要性を説明できることを条件とする。**
採用した場合は、`templates/comparison.md` の「アンチパターンに該当する採用」欄に理由を残す。

抽象的な原則(「装飾には理由を」)だけでは、これらは止まらなかった(dashboard-001)。**作ったあとに、下の「AI典型」を実際に数えて確認する。**

## AI典型(作ったあとに数える)

指示がないと、モデルは学習データの平均を出す。その平均には見覚えのある型がある。以下は、実験で実際に出たもの、または調査で典型として挙がったもの。

| 典型 | 確認の仕方 | 既定の上限 |
|---|---|---|
| 左(片側)だけの色線。パネル・カード・行・メモの左に付ける | CSS の `border-left` と、`inset Npx 0 0` の内側の影を数える | 0。使うなら目的を説明できる1種類だけ(例: 一覧の中で期限切れの行だけ) |
| 淡い背景＋濃い文字のバッジを、すべての状態に使う | 状態の数だけ薄い背景色があるか | 色の面は「注意」の段階だけ。それ以外は文字色・記号で |
| 強調の入れ子。親(パネル)と子(行)の両方に線・色・背景 | 囲みの中の行にも線や背景があるか | 0 |
| 全行に同じ装飾を繰り返す(バッジ・アイコン・ラベルが毎行3つ以上) | 1行の中の装飾要素の数 | 1行あたり、文字以外の装飾は2つまでを目安 |
| どこでもカード / カードの入れ子 / 同じ形のカードの並び | 意味の違う情報が同じ形の箱に入っていないか | 囲みは意味の単位だけ、1段 |
| 囲みゼロ(全部を罫線と余白だけにする) | 管理画面なのに、囲まれた領域が1つもないか | 管理画面では、主要な領域は囲む |
| 要件にない、動かない飾り(検索欄、通知、メニュー「…」) | 要件と照らし合わせる | 0。必要なら仮定として明示する |
| 同じ情報の繰り返し(見出しを言い直す導入文、同じメモを2か所に出す) | 同じ文字列が2回出ていないか | 0。下の「要件の写し方の典型」も見る |
| 大きな数字＋小さなラベルの「ヒーローメトリック」、均等幅の指標カードの列 | | 焦点の1か所だけ。下の「数字の看板」を見る |
| 「技術っぽさ」のための等幅フォント | 等幅がコード・ID以外に使われていないか | コード・ID・時刻の桁揃えだけ |
| 紫〜青のグラデーション、ガラス風、光る縁取り、汎用的な影 | | 0 |
| 別の種類の画面の見た目を借りる(管理画面を、紙色・明朝・朱色の「記事風」にする) | 一瞬見て、何の画面に見えるか | 0 |

## 要件の写し方の典型(どの種類の画面でも)

AI は、要件の1項目を、そのまま画面の1部品にしがち。「◯◯が分かること」と書かれると、◯◯専用の目立つ箱・区切り・説明文を作る。結果として、主役(その画面の本体)とは別に「お知らせ」の層ができ、主役と同じ内容を2回見せることになる。

管理画面に限らず、LP、フォーム、設定画面、記事、モバイルアプリでも同じ形で出る。

| 型 | どんな形で出るか(例) | 見分け方 |
|---|---|---|
| **数字の看板**: 重要そうな数値を、大きな数字＋小さなラベルの箱にする | 管理画面「7 要対応の注文」/ LP「10,000+ 導入社数」「99.9% 稼働率」の帯 / 設定画面「残り 3 日」の大きな表示 / アプリ「今日の歩数 8,421」 | その数字を、見出しや本文の中に普通の大きさで書いても伝わるか |
| **画面の自己説明**: 画面が自分の作りや並び順を文章で説明する | 「優先度の高い順に並べています」「以下に〜を表示しています」「ここでは〜できます」/ フォーム「以下の項目を入力してください」/ LP の見出しを言い直すだけのリード文 | その文を消して、困る人がいるか。並び順や操作は、見た目(列の見出し、並び替えの表示、ラベル)で伝わっていないか |
| **要約の二重化**: 本体と同じ内容を、要約の箱にも出す | 一覧の上の「要対応の注文」の箱+同じ注文が一覧にも / LP の冒頭の特長3つ+下の特長セクション / 設定画面の上の「現在の設定」カード+同じ設定項目 / 記事の冒頭の要点+本文の繰り返し | 箱の中身が、本体のどこかにそのまま出ていないか |
| **属性による分割**: 本体を、すでに切り替えられる属性でさらに区切る | 一覧を「要対応」と「その他」に分ける(タブで絞り込めるのに)/ 商品一覧を「おすすめ」と「すべて」に分ける(並び替えがあるのに)/ フォームの注意書きを項目ごとの警告ボックスにする | その区切りと同じことを、タブ・絞り込み・並び替え・既定の表示で実現していないか |

### 代わりにすること

- **まず主役の中で表現する**: 注意が必要なものは、主役(一覧の行、本文、フォームの項目)の中に、印・色・並び順で示す。別の箱を作るのは、主役の中では表現できない場合だけ。
- **切り替えの仕組みに任せる**: 「要対応だけ見たい」は、タブや絞り込み、既定の表示(最初に選ばれているタブ、既定の並び順)で実現する。本体を分割しない。
- **数字は文脈の中に置く**: 件数や統計は、見出しやタブのラベル(「要対応 7」)、本文の中に、普通の大きさで書く。看板にするのは、その画面の焦点(`03-design-protocol.md` Step 2)が「その数字そのもの」の場合だけ。
- **説明文の代わりに見た目で伝える**: 並び順は列の見出しの印、操作は分かりやすいラベル、注意は位置と色で伝える。

確認の質問: **「この箱・区切り・文を消したら、何が失われるか」**。主役ですでに伝わっているなら、消す。

## レイアウト

- 意味の異なる情報をすべて同じ形のカードに入れる。
- どの画面でも同じ3列・4列のカードグリッドを使う。
- すべてのページに大きなタイトルと説明文を置く。
- 情報量にかかわらず、過剰に広い余白を設ける。逆に、1画面に収めるために情報を詰め込みすぎる。
- 実際の利用目的より、見栄えを優先した構造にする。

## 色と装飾

- 強調色を多用し、視覚的な優先順位を曖昧にする。
- 背景、カード、ボタン、バッジのすべてに装飾を加える。
- すべてのコンポーネントを大きな角丸にする。

## タイポグラフィと情報設計

- すべてを大きな見出しと短いキャッチコピーで表現する。
- 実際には必要な情報がないのに、見た目を埋めるための説明文を追加する。
- 実際のデータや要件を確認せず、ダミーの指標やグラフを並べる。
- 見た目を整えるために、操作や情報の分かりやすさを犠牲にする。
