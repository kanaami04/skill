# デザイン案の生成プロトコル

同じ要件から、共通の土台を決めたうえで3案を作り、比較して、ユーザーが選ぶ。選んだ案は修正し、仕様にまとめる。

ここで作る案は、本実装の前に画面を決めるための**単体のHTML案**である。本実装はこのプロトコルの範囲外とする。

## Step 1：要件を理解する

案を作る前に以下を整理する。`templates/requirements.md` の形式の画面要件が渡されていれば、それを使う。

- 画面の目的
- 対象ユーザーと利用頻度
- 主要な操作
- 表示する情報と優先順位
- 必要な状態(初期、読み込み、空、エラー、成功など)
- 本実装の技術スタックと既存プロジェクトの制約(案の作り方ではなく、仕様の書き方に影響する)
- レスポンシブ対応の必要性

不明な点は仮定として記録する。実装前にすべての質問をする必要はないが、重要な不明点を黙って確定しない。

## Step 2：共通の土台を決める

3案に分かれる前に、全案で共有する判断を決めて、`comparison.md` の冒頭に書く。ここが崩れると、どの案も外れる。

1. **画面の種類と守る慣習**(Rule 01): 例「管理画面。左ナビ、ページ見出し、主要な領域は囲む、比較する情報は表」。
   - **主役**(Rule 02): その画面の本体は何か。例「注文一覧」「記事の本文」「申し込みフォーム」。要件の各項目を、主役の中でどう表現するかを先に考える。
2. **焦点**(Rule 03): 最初に目に入れたい1か所。例「今日対応すべきタスクの件数と最優先の1件」。
3. **囲む単位**(Rule 04): どの領域を囲むか。入れ子にしない。
4. **強調の段階**: 焦点 / 注意 / 通常の3段階を、それぞれ何で表すか(大きさ、色、太さ)。アクセント色は1つ。
5. **出さないもの**: `02-anti-patterns.md` の AI典型のうち、この画面で特に出やすいもの。

## Step 3：3案の方向性を決める

3案は、**見せる UI と実務の UI の配分**を変える。見た目の型(「エディトリアル風」など)は指定しない。3案とも Step 2 の土台を守る。

### A. Practical(実務寄り)

- 毎日何度も使う人の、処理の速さを優先する。
- 表・リスト・コンパクトな操作領域を使い、情報を一覧で比べられるようにする。
- ただし、密度を上げても焦点は1つ残す。1画面に収めるために情報を詰め込みすぎない。

### B. Balanced(折衷)

- 実務の構造に、第一印象を良くする要素を足す。余白、文字の階層、ブランド色の一点使いなど。
- 初めて見る人にも、毎日使う人にも無理がない構成にする。

### C. Presentable(見せる寄り)

- 第一印象と、プロダクトの個性を優先する。見た目の良さは、使いやすさの評価そのものを上げる(美的ユーザビリティ効果)。
- ただし、画面の種類の慣習(Step 2-1)は守る。別の種類の画面に見えたら失敗。
- 情報は絞り、文字は大きめにしてよい。

これらは固定のテンプレートではない。画面の目的に応じて変えてよい。変えた場合は、比較記録に理由を書く。

## Step 4：各案を独立して作る

- 3案とも同じ機能要件を満たし、同じデータを使う。
- 色や角丸だけを変えた案を作らない。情報の配置、レイアウト、文字、情報密度を変える。
- **各案について「普段どおりに作った場合と何が違うか」を一言で説明できるようにする。** 説明できない案は、ありがちな画面になっている。
- 各案は単体のHTMLファイルにする。CSSは`<style>`に書き、JavaScriptは必要な場合だけVanilla JSで書く。
- ビルドツール、フレームワーク、外部UIライブラリを使わない。外部フォントや外部画像などのネットワーク依存を原則避ける。
- 画面の見た目だけでなく、ブリーフで指定された主要な操作は動くようにする。

### 案の置き場所(既定)

ブリーフに指定があればそれに従う。指定がなければ以下に置く。

```
experiments/<実験ID>/
├── requirements.md      # 画面要件(Baseline にも渡せる)
├── comparison.md
├── experiment-log.md    # 実験するときだけ。実験設計(評価者用)もここに書く
└── rules/
    ├── variant-a.html   # A. Practical
    ├── variant-b.html   # B. Balanced
    └── variant-c.html   # C. Presentable
```

既存のプロジェクトの中で使う場合も、既存ファイルには触れず、この形の専用ディレクトリに置く。

## Step 5：ブラウザで検証する

- 各案を同じビューポートで表示する。可能ならデスクトップとモバイルの両方で確認する。
- 横スクロール、文字のはみ出し、レイアウト崩れ、主要な操作を確認する。
- **第一印象の確認**: 最初の画面のスクリーンショットを見て、次の2つに答える。
  - 何の画面に見えるか(Step 2-1 の種類に見えるか)。
  - 最初に目が行くのはどこか(Step 2-2 の焦点と一致するか)。
- **AI典型を数える**(`02-anti-patterns.md`): 左の色線、淡いバッジ、強調の入れ子、動かない飾りなど。上限を超えたら直してから報告する。
- **実際に画面を表示できていない場合は、表示確認済みと報告しない。** 確認できた範囲と、できなかった範囲を分けて書く。

## Step 6：比較して採用案を選ぶ

`templates/comparison.md` を使い、各案について記録する。

推奨案は、次の順で判断する。

1. 画面の種類に見えるか(見えない案は推奨しない)
2. 焦点が伝わるか
3. 要件に合っているか
4. プロダクトらしさがあるか

「仕様にしやすい」「装飾が少なく無難」は、推奨の理由にしない。

**Claude の自己評価は、人間の評価より高く出やすい**(dashboard-001 では、ほぼすべての画面で1点以上高かった)。点数で断定せず、第一印象と気になる点を具体的に書いて、判断をユーザーに渡す。

**ユーザーが最終決定できるようにする。ユーザーの明示的な承認なしに、選定結果を本番実装へ統合しない。**

## Step 7：採用案を修正する

- 修正の指摘が、案の方向性(Step 3)と矛盾する場合は、**指摘を優先する。** 方向性を守るために、原案の構造に縛られない。必要なら構造ごと作り変える。
- 修正の前後で、見て分かる違いを出す。違いが小さいと「修正してもほとんど変わらない」と受け取られる。
- 他の案に、指摘を解決している部分があれば取り込む。
- 修正のたびに、Step 5 の第一印象の確認と AI典型の数え直しをする。
- 指摘を直す過程で、前の指摘が直ったものを壊さない(例: 線を外しすぎて、管理画面らしさまで消す)。

## Step 8：デザイン仕様を出力する

ユーザーが採用を決めたら、`templates/design-spec.md` に以下をまとめる。この仕様は、後で本実装する人(またはClaude)が、HTML案を見なくても判断を再現できる粒度で書く。

- デザインの意図
- 共通の土台(Step 2)
- カラーと使用ルール
- タイポグラフィの階層
- 余白とサイズのルール
- 角丸、境界線、影のルール
- コンポーネントの使い分け
- レスポンシブの方針
- 避けるべきアンチパターン
- 実装時に維持すべき条件

必要に応じてMarkdown、CSS変数、JSONなどで出力する。
