# 実験方法

ルール適用によって品質が上がり、修正時間が減ったかを検証する。

## 比較する2条件

同じ画面要件を2通りの方法で作って比較する。

**Baseline**
普段どおりClaude Codeに画面を生成させる。このSkillのルールは使わない。

**Rules**
本ルールとデザイン案の生成プロトコル(`03-design-protocol.md`)を適用し、3案から採用案を選んで修正する。

## 条件をそろえる

結果の差がルール由来かどうかを見るため、以下をそろえる。

- **画面要件は `requirements.md` として独立させ、Baseline にはそのファイルだけを渡す。** 評価基準や比較方法は実験ログの「実験設計」に書き、Baseline には渡さない(同じファイルに書くと、Baseline も読んでしまう)。
- **実験ログは、実験フォルダの外(`experiment-logs/<実験ID>.md`)に置く。** 実験フォルダの中に置くと、フォルダを調べた流れで両条件とも読んでしまう(order-list-001 で発生)。
- Baseline と Rules は、それぞれ**新しいセッション**で実行する。
- 使うモデル、ビューポートを同じにする。
- 自動で動くデザイン系のプラグイン(例: `frontend-design`)は、両条件とも無効にする。
- Baseline のプロンプトは「requirements.md の画面を作って」程度にとどめる。ルールの要素を混ぜない。
- **条件に関わるファイル(調査メモ、他の案、ルール)を IDE で開いたままにしない。** 開いているファイルの情報は、両方のセッションに伝わる(dashboard-001 の修正2回目で、Rules だけが調査メモを読んだ)。
- 修正の指示は、両方に同じ内容を、評価者の言葉のまま渡す。ルールの考え方を Baseline 側の指示に混ぜない。
- 修正指示で点数を書くときは「総合 3/5」と書く(「3点です」は「指摘が3つ」と読まれた)。

## 記録する項目

`templates/experiment-log.md` をコピーした `experiment-logs/<実験ID>.md` に記録する。

- 初回生成にかかった時間
- 修正ごとの時間と内容
- 採用可能な画面になるまでの時間(壁時計と、生成・修正の実作業時間の両方)
- 見た目の修正回数、機能・レイアウトの修正回数
- 生成案の間に明確な違いがあったか
- 第一印象と総合点(人間と Claude を分けて)
- 採用理由と却下理由
- 条件の逸脱

時刻は、Claude Code のセッション記録(`~/.claude/projects/<プロジェクト>/<セッションID>.jsonl`)のタイムスタンプから取れる。スクリーンショットと変更履歴(修正ごとのコミット)を残す。

## 評価の進め方

- **人間の評価を先に書く。** Claude の評価を先に読むと引っ張られる。
- 人間は定性的に、第一印象から書く。Claude はチェックリストと AI典型の数で書く。両者の食い違いを記録する。
- Claude の評価は、人間より高く出やすい。採用可能の判定は人間の点数で行う。

## 解釈の注意

- 1種類の画面だけで結論を出さない。複数の画面・プロジェクトで再現性を確認する。
- 時間はユーザーの待ち時間と手作業を含めて測る。中断が入った場合は、実作業の時間でも比べる。
- Rulesは3案を作る分、初回生成は長くなりやすい。「採用可能になるまでの時間」と「修正回数」で比べる。
- 差が出なかった場合も、Baseline が勝った場合も、その結果を記録する。ルール改善の材料になる。
