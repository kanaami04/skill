# 基本原則

## 目的

AIが生成するWeb UIにありがちな画一的なデザインを減らし、プロダクト固有の目的・ユーザー・情報構造に適した、意図のあるUIを効率よく作る。

## Rule 01：画面の種類の慣習を守り、差別化は中身で出す

- まず「何の画面に見えるべきか」を決める(管理画面、LP、記事、設定画面など)。
- その種類の**構造の慣習**は崩さない。管理画面なら、左または上のナビ、ページの見出し、囲まれた領域、表やリスト。ユーザーはほかのアプリで覚えた期待を持って画面を見る。
- 個性は、構造ではなく、色・文字・データの見せ方・重要な操作で出す。
- 個性を出した結果、別の種類の画面に見えたら失敗とみなす(例: 管理画面が記事やニュースサイトに見える)。

## Rule 02：目的からレイアウトを決める

- 最初に画面の目的、対象ユーザー、主要な操作を整理する。
- 表示する情報とその優先順位を明確にする。
- レイアウトは、情報の性質とユーザーのタスクに合わせて決める。比較する情報は表・リスト、要約の単位はカード。
- 情報を絞る。全部を同じ重みで並べず、常に見せるもの・求めに応じて出すものに分ける。
- 画面の主役(一覧画面なら一覧、記事なら本文、フォームなら入力項目)を決め、主役を画面の中心に置く。要件の1項目ごとに専用の箱を作らず、まず主役の中で表現できないか考える(`02-anti-patterns.md`「要件の写し方の典型」)。

## Rule 03：焦点を1つ決め、強調に段階を付ける

- 各画面で「最初に目に入れたい1か所」を先に決める。強い色・大きさ・太さは、そこに集める。
- 強調は多くても3段階(焦点 / 注意 / 通常)にする。すべてを強調すると、何も目立たない。
- 色は補助の手がかりにする。意味は、位置・大きさ・形・文字でも伝える。
- 文字サイズと余白は、情報の重要度に合わせて使い分ける。本文が小さすぎると、整っていても読む気が起きない。

## Rule 04：囲みは意味の単位だけ、1段で

- 囲み(枠・背景色・影)は、まとまりを示す強い手がかり。意味のある単位(例: 今日のタスク、プロジェクト一覧)だけを囲む。
- 囲みを入れ子にしない。親(パネル)と子(行)の両方に枠・線・色を付けない。
- 全部を囲むのも、全部外すのも避ける。囲みをゼロにすると、管理画面らしさが消える。

## Rule 05：装飾には理由を求める

- 線、色の面、バッジ、アイコン、影、角丸は、目的がある場合だけ使う。装飾なしで伝わるかを先に考える。
- 個別には良い装飾でも、全行に同じように繰り返すと、見づらくなる。
- 要件にない、動かない飾り(使えない検索欄、通知ボタンなど)で「それらしさ」を足さない。
- 具体的な典型は `02-anti-patterns.md` を見る。

## Rule 06：プロダクト固有の特徴を反映する

- 業界、対象ユーザー、情報の性質、利用頻度、プロダクトの個性をデザインに反映する。
- 実際の用途に合う情報密度、ナビゲーション、操作方法を選ぶ。
- ただし Rule 01 の範囲内で行う。
- 要件が不明な場合は仮定を明示し、勝手に事実を作らない。
